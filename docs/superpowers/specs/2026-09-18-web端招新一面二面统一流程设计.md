# Web端招新一面二面统一流程设计

## 1. 目标

统一 Web 管理端招新管理的一面、二面业务模型，消除当前两套结果接口、权限判断和状态命名并存的问题。

本次设计只覆盖 Web 管理端招新管理，不调整 UniApp 页面。核心原则是：每个志愿作为一条独立面试轨道处理，候选人最终只产生一个录用结果并只发送一次结果邮件。

## 2. 核心业务模型

每位候选人最多拥有两条志愿轨道：

- 第一志愿轨道
- 第二志愿轨道

每条轨道独立保存：

- 志愿顺序与部门
- 一面面评
- 一面结果
- 是否进入二面
- 二面分数
- 二面录用结果

候选人总记录保存：

- 最终录用部门
- 最终报名状态
- 邮件发送状态与发送时间

面试结果统一使用 `PENDING`、`PASS`、`OUT`。历史 `FAIL` 数据按 `OUT` 兼容读取，新的前后端请求不再写入 `FAIL`。

## 3. 一面流程

### 3.1 页面功能

普通部门账号拥有三个功能：

1. 阅览简历
2. 编辑面评
3. 查看面评

部门权限必须隔离：

- 普通部门账号只能编辑自己所属部门的面评。
- 普通部门账号只能查看自己所属部门对该候选人的面评。
- 普通部门账号不能查看或修改其他部门面评。

管理员账号额外拥有一面 Pass/Out 权限。第一志愿与第二志愿必须分别判定，不能互相覆盖。

管理员可以查看两个志愿部门的面评；管理员如果没有所属部门，只能查看面评，不能代替部门成员编辑面评。

### 3.2 晋级规则

一面两条志愿独立产生结果：

| 第一志愿 | 第二志愿 | 二面资格 |
| --- | --- | --- |
| PASS | PASS | 两个志愿都进入二面 |
| PASS | OUT | 只有第一志愿进入二面 |
| OUT | PASS | 只有第二志愿进入二面 |
| OUT | OUT | 候选人淘汰 |

未完成必要判定时，候选人保持一面处理中状态，不提前生成最终二面名单。

## 4. 二面流程

二面列表只展示至少有一条志愿在一面获得 `PASS` 的候选人。一面 `OUT` 的志愿不能评分，也不能执行二面录用决定。

### 4.1 面试评分

二面评分入口命名为“面试评分”，同时承担查看和编辑分数的功能。

- 每个“候选人 + 志愿部门”只有一个最终分数。
- 分数为 0 至 100 的整数。
- 不保存多位面试官的独立分数，不计算平均分。
- 本部门具备评分权限的人员均可查看和修改本部门分数。
- 后一次保存覆盖当前分数。
- 后端记录最后修改人和最后修改时间。
- 第一志愿和第二志愿的分数独立保存。
- 二面录用结果确定后，该志愿分数锁定，不允许继续修改。
- 分数未填写时，管理员不能对该志愿执行二面 Pass/Out。

### 4.2 录用决定

只有管理员账号可以操作“录用决定”。

管理员必须明确选择志愿部门，再对该志愿执行 `PASS` 或 `OUT`。两个志愿的二面结果独立保存，不能互相覆盖。

最终结果汇总规则：

| 第一志愿二面结果 | 第二志愿二面结果 | 最终结果 |
| --- | --- | --- |
| PASS | PASS | 录用第一志愿 |
| PASS | OUT 或未进入二面 | 录用第一志愿 |
| OUT 或未进入二面 | PASS | 录用第二志愿 |
| OUT | OUT | 淘汰 |

录用决定只保存结果，不自动发送邮件。

## 5. 邮件流程

每位候选人最终只发送一次结果邮件。

### 5.1 发送条件

- 所有进入二面的志愿都已完成评分和录用决定。
- 后端已经根据结果确定最终录用部门或淘汰结果。
- 该候选人尚未成功发送最终结果邮件。

条件不满足时，前端禁用发送按钮并显示原因；后端必须再次校验并拦截非法或重复发送。

### 5.2 模板与附件

- 邮件正文使用后端提供的固定模板。
- 双 `PASS` 时，后端返回第一志愿的通过模板。
- 单志愿 `PASS` 时，后端返回对应志愿部门的通过模板。
- 全部 `OUT` 时，后端返回淘汰模板。
- 录用邮件必须附带群二维码图片。
- 群二维码附件允许 JPG、JPEG、PNG，大小不超过 5 MB。
- 淘汰邮件不要求群二维码附件。

前端发送弹窗展示收件人、最终部门、模板预览、二维码附件和发送按钮。模板正文由后端决定，前端不自行拼接业务模板。

### 5.3 可靠性

- 发送中锁定按钮，防止重复点击。
- 后端实现幂等校验，成功发送后拒绝重复发送。
- 邮件发送失败不回滚已经保存的一面、评分或录用结果。
- 发送失败时保留弹窗数据，允许再次尝试。
- 发送成功后展示已发送状态和发送时间。

## 6. 页面与按钮设计

### 6.1 一面操作

普通部门账号：

`阅览简历｜查看面评｜编辑面评`

管理员账号：

`阅览简历｜查看面评｜Pass｜Out`

管理员拥有所属部门且具备面评编辑权限时，可以编辑所属部门面评。

### 6.2 二面操作

普通部门账号：

`阅览简历｜面试评分`

管理员账号：

`阅览简历｜面试评分｜录用决定｜发送邮件`

按钮保持现有 Web 管理端深色与橙色视觉体系：

- 阅览、查看使用浅色描边按钮。
- 编辑面评、面试评分使用橙色主按钮。
- Pass 使用绿色按钮。
- Out 使用红色描边按钮。
- 发送邮件使用深色主按钮。
- 同一行按钮统一高度、圆角和间距，不使用拥挤的纯文字链接。
- 危险操作必须有确认弹窗、加载状态和重复点击保护。

## 7. 权限边界

前端不再根据 `ceo`、`qt_mgmt`、`qt_manager` 等角色名称自行推断业务权限，应以服务端返回的权限标识控制操作，例如：

- 查看招新名单
- 查看/编辑面评
- 查看/编辑评分
- 执行录用决定
- 发送结果邮件

后端必须同时执行权限与部门范围校验。隐藏前端按钮不能替代服务端鉴权。

普通部门账号只能访问本部门轨道。管理员可以查看全部志愿轨道并执行结果判定，但不能在没有所属部门的情况下冒充部门人员编辑面评或评分。

## 8. 前后端数据流

### 8.1 名单

名单接口返回候选人和两条志愿轨道的完整状态。二面查询必须在服务端筛选一面已通过的轨道，不能由前端加载全部报名后自行推断。

### 8.2 面评

一面面评按“报名 ID + 志愿部门 + 操作人”保存。查看接口按当前用户部门范围过滤；管理员查看时可以按志愿部门切换。

### 8.3 评分

二面分数按“报名 ID + 志愿部门”唯一保存，更新时覆盖原分数，并记录最后修改人和时间。

### 8.4 录用决定

一面、二面结果统一使用同一套轨道结果模型和规范状态，不再让一面与二面分别维护不兼容的 `FAIL/OUT` 逻辑。

### 8.5 邮件

邮件分为预览和确认发送两步。预览接口根据服务端最终结果返回模板和最终部门；发送接口接收二维码附件并进行完整性、权限和幂等校验。

## 9. 异常处理

- 一面结果未完整时，不生成错误的二面资格。
- 一面未通过的轨道禁止二面评分和录用决定。
- 分数为空时禁止录用决定。
- 二面结果未完整时禁止发送邮件。
- 越权访问其他部门面评或评分时，由后端拒绝。
- 请求失败时保留用户已输入内容并给出明确提示。
- 并发修改分数时以最后一次成功保存为准，并刷新最后修改人和时间。

## 10. 验收与测试

至少覆盖以下场景：

1. 一面四种 Pass/Out 组合及对应二面资格。
2. 双 Pass 时两个志愿均进入二面。
3. 普通账号只能查看和编辑本部门面评。
4. 二面两个志愿分别保存 0 至 100 的唯一分数。
5. 分数可多次修改，录用决定后锁定。
6. 无分数时不能执行录用决定。
7. 二面四种结果组合及最终部门选择。
8. 双 Pass 时最终选择第一志愿。
9. 每位候选人最终只发送一封邮件。
10. 录用邮件必须包含有效二维码附件。
11. 邮件失败不影响已保存结果。
12. 历史 `FAIL` 状态按 `OUT` 正确兼容。
13. 前端按钮权限和后端接口权限保持一致。

## 11. 不在本次范围内

- UniApp 招新流程改造。
- 邮件模板后台编辑器。
- 多面试官独立评分与平均分。
- 一面文字面评以外的新评价维度。

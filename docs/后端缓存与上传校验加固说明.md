## 1. 改动前的真实状态（盘点结论）

**已有 Redis 使用的地方全在上游若依层，业务层 0 缓存：**

| 用途 | 位置 | 当时 TTL |
|---|---|---|
| 登录态 LoginUser | `TokenService.java` | 30min 滑动 |
| 验证码 | `CaptchaController.java` | 2min |
| 密码错误计数 | `SysPasswordService.java` | 10min |
| 防重复提交 | `SameUrlDataInterceptor.java` | 注解 interval |
| 限流脚本 | `RateLimiterAspect.java` | 注解 time |
| `sys_config` | `SysConfigServiceImpl.java` | **永久** |
| `sys_dict` | `DictUtils`（启动预热） | **永久** |

`ruoyi-qt` 14 个 Controller / 89 个 mapping **没有任何缓存**。

三个必须先处理的隐患：

1. `RedisConfig.java` 有 `@EnableCaching`，但**没有定义 CacheManager**。此时随手加 `@Cacheable` 会走 Spring Boot 自动配的 `RedisCacheManager` —— **默认永不过期**。
2. Redis 是 `maxmemory 128mb` + `volatile-lru`：**只有带 TTL 的键参与淘汰**。业务缓存若无 TTL，塞满后被淘汰的反而是带 TTL 的 `login_tokens:` → 表现为「全员随机掉线」。
3. `@RateLimiter` / `@RepeatSubmit` 两个注解的切面都在，但**全项目 0 处使用**。

## 2. 缓存设计

### 2.1 三类数据，三种处理

| 类别 | 处理 | 覆盖 | TTL |
|---|---|---|---|
| **A 无分页**（统计/详情/配置） | `@Cacheable` + `@CacheEvict` | `/dashboard/stats`、`/qt/interview/admin/statistics`、`/qt/member/cohorts`、`/system/payment-config/{id}`、`/system/book/{id}`、`/system/activity/{id}`、`/qt/interview/my`、`/qt/interview/myResults` | 30–600s |
| **B 分页列表** | 方法体内 `QtQueryCache.loadPage` | `/system/book/list`、`/system/activity/list`、`/system/workstation/list` | 60–120s |
| **C 明确不缓存** | 直查 | 所有 `detailList`（管理端要求实时）、`/qt/interview/admin/applications`、`/qt/materials`（列表+详情）、export | — |

缓存名与 TTL 的唯一来源是 `CacheConstants`（`CACHE_QT_*` / `TTL_QT_*`），`RedisConfig` 的 TTL 表和控制器手动缓存共用同一份常量，避免两处漂移。

### 2.2 为什么分页列表不能直接 `@Cacheable`（关键决策）

三点都是硬伤，不是风格问题：

1. **切面顺序不可控**：`@PreAuthorize` 与 `CacheInterceptor` 的先后没有保证。若缓存先于鉴权返回，非管理员可能直接拿到管理员视图（活动列表 `QtActivityController` 里「非管理员强制 `status=PUBLISHED`」就是靠鉴权结果区分 key 的）。
2. **PageHelper 的 ThreadLocal 泄漏**：`startPage()` 在 Controller 里调用。`@Cacheable` 命中时方法体不执行 → 分页 ThreadLocal 没被消费，会污染**同一线程上的下一个查询**（间歇性、极难复现的错页）。
3. **`total` 失真**：PageHelper 返回的是 `com.github.pagehelper.Page`，而 `Constants.java:161` 的 fastjson2 autoType 白名单只有 `"com.ruoyi"`。缓存命中反序列化后退化成普通 `ArrayList` → `BaseController.getDataTable()` 里 `new PageInfo(list).getTotal()` 变成**当页条数**。管理端 8 个 api 文件都读 `response.total`，分页条是 `v-if="total > query.pageSize"` → 翻页控件直接消失。

`QtQueryCache.loadPage` 一次解决三条：缓存判断在鉴权之后的方法体内、命中时根本不执行 `startPage()`、缓存的是**已组装好的整份 `TableDataInfo`**（含正确 total），并按行类型还原成实体，让 Jackson 用与未命中路径完全相同的规则序列化。

### 2.3 key 设计：防串数据优先于命中率

- **指纹用反射收集查询对象的全部非空字段**（`QtCacheKeys.fieldsOf`），而不是手工枚举。原因：手工枚举一旦漏掉某个过滤条件，两个不同结果集会撞同一个 key —— 这是最难排查的一类线上 bug。新增过滤参数自动进 key。
- 指纹再做 SHA-256 截断，避免长 key。
- **凡结果随当前用户数据权限变化的缓存，key 必须带维度**：`/qt/interview/admin/statistics` 内部用 `QtAuthUtils.scopedDepartment()`，key 即 `QtCacheKeys.scopedDept()`。
- 个人维度缓存 key = `userId`（`qt:my:*`）。
- `disableCachingNullValues`：空结果不缓存，所以「查不到」不会被固化成一次数据不一致。

### 2.4 失效矩阵

| 写操作 | 清掉的缓存 |
|---|---|
| 图书 insert/update/delete | `qt:book:detail` + `qt:book:list` |
| 借出/归还（`QtBookBorrowServiceImpl`） | `qt:book:detail` + `qt:book:list`（可借数量会变） |
| 活动 insert/update/delete | `qt:activity:detail` + `qt:activity:list` |
| 工位 insert/update/delete | `qt:workstation:list` |
| 服装款式 insert/update/delete | `qt:item:list`（**预留**：款式列表当前未接读取缓存，见 §2.5） |
| 付款码配置 CRUD | `qt:payment-config` |
| 成员留任 / 换届 `rollover` | `qt:member:cohorts` |
| 面评/录用/最终状态/入职状态 | `qt:recruit:statistics` |
| 学生投递 `saveMyApplication` | `qt:my:application` + `qt:my:profile` + `qt:my:results` + `qt:recruit:statistics` |
| 录入面试结果 `saveInterviewResult` | `qt:my:results` + `qt:recruit:statistics` |

### 2.5 已知不精确之处（诚实记录）

- `qt:item:list` 常量与款式服务里的 `evict` 已就位，但**款式列表本身没接读取缓存** —— 因为 `QtClothingItemController.list` 会调 `fillImageUrl()` 用 `serverConfig.getUrl()`（按当次请求推导）拼绝对地址，缓存住会把第一个访问者的域名烧进 URL。要缓存它得先让图片走相对路径。
- 管理端发布面试结果后，学生侧 `/qt/interview/my` 最多滞后 30 秒（TTL 到期），跨服务按 userId 精确清缓存没做。投递方自己的视图是即时清的。
- 缓存是 Redis 单点，多实例部署时失效是全局一致的（都打同一个 Redis），但 `@Cacheable` 的本地无缓存层，无脏读风险。

## 3. 上传与文件校验

### 3.1 档位

| 场景 | 上限 | 白名单 |
|---|---|---|
| 证件照 / 头像 / 收款码 / 效果图 / 支付凭证 | **5MB** | `IMAGE_EXTENSION`（bmp gif jpg jpeg png） |
| 学习资料 | **20MB** | `DEFAULT_ALLOWED_EXTENSION` |
| 用户导入 | **5MB** | 新增 `EXCEL_EXTENSION`（xls xlsx） |

配套：`spring.servlet.multipart.max-file-size` 10MB→20MB、`max-request-size` 20MB→25MB、nginx `client_max_body_size` 20m→25m。

### 3.2 `FileValidator`（新增，`ruoyi-common/.../utils/file/`）

1. **大小**：按场景档位，不再只有全局 50MB。
2. **文件头魔数**：jpg `FFD8FF`、png `89504E47…`、gif `GIF8`、bmp `BM`、pdf `%PDF`、zip/docx/xlsx/pptx `PK\x03\x04`、rar `Rar!`、gz `1F8B`、bz2 `BZh`、doc/xls/ppt `D0CF11E0`、媒体类 `RIFF`/`ftyp`/`.RMF`/`ID3`/`FLV`/`CWS|FWS|ZWS`；`txt` 无签名 → 要求 `Content-Type: text/*` 且前 16 字节不含 NUL。**后缀与内容不符直接拒**。
3. **图片像素**：`ImageIO.getImageReaders()` 只读文件头拿宽高（不解码整图），单边 ≤4096、总像素 ≤2000 万，防高压缩比巨图打爆解码内存。

接入方式：`FileUploadUtils.upload(baseDir, file, allowedExtension, maxSize)` 新重载；`assertAllowed` 在后缀白名单通过后再调 `FileValidator.validateContent`。
`/common/upload` 与 `/common/uploads` 按 `subDir` 决定「白名单 + 档位」（沿用已有的 `ALLOWED_UPLOAD_SUB_DIRS` 白名单，未指定 subDir 走文档档）。

### 3.3 实测结果

| 用例 | 结果 |
|---|---|
| 40×40 合法证件照 | 接受 |
| 6MB 证件照 | 拒绝（`文件大小超出限制，最大允许 5MB`） |
| HTML 改名 `.png` | 拒绝（`文件内容不是合法的 PNG 格式（疑似改名文件）`） |
| 9000×9000 PNG | 拒绝（`图片尺寸过大（9000×9000），单边最大 4096 像素`） |
| SVG 伪装 `.png` | 拒绝（魔数不符） |
| 真 SVG 用 `.svg` | 拒绝（白名单外） |
| 19MB PDF 走资料档 | 接受 |
| `.html` 走资料档 | 拒绝（白名单外，上游已移除 html） |
| `MZ` 头伪装 `.png` | 拒绝（魔数不符） |

顺手修：超限原本抛 `FileSizeLimitExceededException`，其 i18n 文案带 `<br/>`，会原样显示在前端提示里 → 改抛 `ServiceException` 给干净中文。

## 4. 安全加固（三项均已授权）

| 项 | 改动 | 验证 |
|---|---|---|
| **JWT 密钥** | `application.yml` 的 `token.secret` 从 `abcdefghijklmnop…`（**本仓库是公开 fork，任何人都能拿它伪造管理员 token**）改为 `${TOKEN_SECRET:}`；`run.sh` 用 `${TOKEN_SECRET:?…}` 强制校验，并以**环境变量**注入（不上命令行，避免 `ps` 泄露）；`TokenService.initSecret()` 兜底：缺失/等于上游默认值/短于 32 位 → 随机生成 + 打醒目 WARN | 服务正常启动，登录鉴权通过 |
| **Druid 监控台** | 原 `statViewServlet.enabled:true` + `allow:` 空（全网可访问）+ 口令 `ruoyi/123456`，且 `SecurityConfig` 把 `/druid/**` 设为 permitAll。改为：`enabled: ${DRUID_STAT_ENABLED:false}`、`allow: 127.0.0.1`、口令走环境变量、移除 permitAll、nginx 再加一层 404 | `https://www.quantacenter.com/druid/index.html` → **404** |
| **静态资源通配** | `"/**.html"` 是递归通配（`/任意/深度/evil.html` 都放行），收窄为 `/`、`/index.html`、`/favicon.ico`、`/*.css`、`/*.js`、`/profile/**`（前端由 nginx 直出，老 `ruoyi-ui` 已确认弃用） | 未登录访问 `/readme.html`、`/any/deep/evil.html` → **401**；`/profile/**` 仍可达 |

附带：

- `LimitType.USER`（新增）：按登录用户分桶，未登录自动退回 IP。**不用纯 IP 维度的原因**：校园网/实验室共用一个公网出口，按 IP 限流会把整栋楼一起限掉。
- 启用了此前 0 处使用的注解：`/login` 20 次/60s、`/register` 5 次/小时（IP）、`/common/upload` 30 次/60s、`/uploads` 10 次/60s、`/qt/interview/apply` 10 次/60s；`@RepeatSubmit` 加在投递、下单、借阅、工位预约、活动报名。
- `PageUtils.startPage()`：`pageSize` 上限 **1000**、`pageNum` 下限 1。上限取 1000 而不是 200，是因为小程序图书页现用 `pageSize=500`（`Quanta-uniapp/src/api/library.ts:43`），设小了会**静默截断**列表。

## 5. 容量参数（100–300 人非同时在线）

先说结论：这个量级本身不靠缓存撑。按 300 注册 / 日活 60% / 人均 20 请求 / 集中 2 小时 ≈ 平均 0.5 QPS，招新开放整点按 50 倍突发 ≈ 25 QPS。所以参数改动主要防**单点放大**：

| 参数 | 改前 | 改后 | 原因 |
|---|---|---|---|
| Tomcat `max-threads` | 800 | 200 | 2 核机器上 800 线程是幻觉，只会加剧数据库连接争抢 |
| Tomcat `accept-count` | 1000 | 200 | 过载时快速失败优于长时间排队 |
| Druid `maxActive` | 20 | 50 | 20 连接 vs 200 线程，一次慢查询/导出就能让全站排队到超时 |
| Druid `maxWait` | 60s | 10s | 60s 等待 = 用户看到「转圈一分钟然后失败」 |
| Redis `maxmemory` | 128mb | 256mb | 业务缓存 + 登录令牌共存，留余量；同时全库键都带 TTL，`volatile-lru` 才安全 |
| nginx `/admin/assets/` | `no-cache` | `immutable, max-age=31536000` | vite 产物带 hash，文件名即版本；`index.html` 仍 `no-cache`，发版不会拿旧 JS |
| nginx `/profile/` | 无缓存头 | `max-age=604800` + `nosniff` | 证件照/图片重复加载，且防上传件被当脚本执行 |

## 8. 踩坑记录（对同学最有价值的部分）

1. **Spring Boot 4 用 Jackson 3**：`com.fasterxml.jackson.databind.ObjectMapper` 在这个工程里**根本没有对应 bean**（jar 内同时有 jackson 2.21 与 3.1.2，Boot 4 自动配置的是 `tools.jackson`）。给缓存注入 Jackson 2 的 mapper 会直接启动失败（`No qualifying bean of type ObjectMapper`）。最终改用 fastjson2 显式序列化 + 按目标类反序列化，不依赖 autoType。
2. **`@Cacheable` 的 `key` 本身就是 SpEL，不能再套 `#{}`**：写成 `key = "#{T(...).m()}"` 会抛 `SpelParseException: EL1043E Unexpected token`，接口直接 500。
3. **用通用 Map 反序列化会改变响应结构**：`JSON.parseObject(json, TableDataInfo.class)` 后 `rows` 是 `JSONObject`，导致响应凭空多出 `"params": {}`（`BaseEntity` 的字段）。必须按行类型 `toJavaList(QtBook.class)` 还原成实体，让 Jackson 用与未命中路径完全相同的规则输出。契约 diff 归零就是这一步带来的。
4. **Redis 逻辑库选错**（§6.1 的 db1/db0），一度误判「缓存完全没生效」。
5. **Windows 侧写 `.env` 用 `Add-Content` 会引入 CRLF**，`TOKEN_SECRET` 尾部混进 `\r`（长度 64→65，签名密钥被污染）。已规范化；后续给服务器写文本文件优先用 LF。

## 9. 遗留与建议

1. **款式/付款码列表要缓存需先解耦图片 URL**：把 `fillImageUrl` 改成只存相对路径、由前端拼域名（或固定 `server.url`），否则缓存会把首个访问者的域名烧进 URL。
2. **`/qt/materials/{id}` 线上一直是 500**（资料表为空时的既有 NPE，与本轮无关，改动前后一致），建议顺手修。
3. **安全组 22 端口仍是 `0.0.0.0/0` + 密码登录**（阿里云控制台已标黄）。这台跑着 MySQL/Redis 与上传目录，建议限源 IP 或改密钥（`.env` 支持 `ECS_KEY_FILE`）。
4. **生产 Swagger 建议关掉**：`springdoc.swagger-ui.enabled: false`（目前仍 permitAll，等于公开整份接口面）。
5. **验证码开关**：线上 `sys.account.captchaEnabled=false`（`initdb/07_disable_captcha.sql` 的测试便利脚本）。现在 `/login` 有了 IP/用户维度限流，但仍建议上线前恢复验证码并下线该脚本。
6. **小程序侧**（见 `docs/简历投递数据打通待办.md` §5）：证件照建议 `uni.compressImage({quality:80})` 后再传，避免新生手机原图撞 5MB 档；投递失败要把后端 `msg` 原样显示。

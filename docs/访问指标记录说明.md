# 访问指标记录说明

> 本文日期：2026-09-15
> 范围：100–300 人容量结论 + 后端访问指标（QPS / 延迟 / 错误率）采集与查询

## 1. 容量结论（100–300 人）

**可以支撑。** 这里的「100–300 人」指注册规模 / 日活，不是 300 人同时狂点接口。

估算（与 `docs/后端缓存与上传校验加固说明.md` §5 一致）：

- 300 注册 × 日活 60% × 人均 20 请求 / 集中 2 小时 ≈ **平均 0.5 QPS**
- 招新开放整点按 50 倍突发 ≈ **峰值 25 QPS**
- 线上压测：50 并发 × 2000 请求，**0 错误、103.7 QPS**，相对峰值约 4 倍余量

当前单机（2C4G ECS + 单 Java + MySQL + Redis）关键上限：Tomcat 线程 200、Druid `maxActive` 50、MySQL `max-connections` 100、Redis 256mb。真正瓶颈在数据库连接，不在 HTTP 线程。JVM 堆 1G、InnoDB 缓冲池 512M。

使用前提：

- 不是 300 人同时在线写接口。若招新整点几百人同时登录/投递，校园网共享出口 IP 可能触发 `/login` 按 IP 限流（20 次/60s）误伤。
- 本方案只用内存计数 + 每分钟落库，不接 Prometheus/Grafana。2C2G 时期压测后约 1.1G/1.6G；升到 4G 后余量主要给 JVM 堆与 InnoDB 缓冲池。
- 若依自带 `/monitor/server` 是点一下才采样，`@Log` 操作日志只记带注解的后台写操作，拿不到全站 QPS。真实流量看本方案的 `qt_access_metric`。

## 2. 指标怎么记

每个请求只做内存计数，**不写库**。每 60 秒把窗口快照写入 `qt_access_metric`，并打一行 INFO：

```
access-metric qps=.. avg=.. max=.. err4=.. err5=.. inFlightMax=.. dbActive=..
```

- 全局一行 `uri='*'`：QPS、4xx/5xx、平均/最大耗时、窗口内最大并发、JVM 堆、Druid 活跃连接
- 本窗口请求量 Top 20 的 URI（Spring 路径模板，例如 `/qt/book/{bookId}`）

开关（`application.yml` → `qt.metrics`）：`enabled` / `window-seconds` / `top-uris` / `retain-days`。出问题改 `enabled: false`。

错误率按 **HTTP 状态码** 统计。若依业务失败经常仍是 HTTP 200 + `code≠200`，不会计入 4xx/5xx。

## 3. 查询

管理端「访问指标」页（权限 `qt:metrics:list`，admin / CEO）：

- `GET /qt/metrics/latest` 当前未落库窗口
- `GET /qt/metrics/list` 历史全局（默认近 24 小时）
- `GET /qt/metrics/uris` 时间范围内热点 URI

默认保留 30 天，每天 03:15 清理。

## 4. 已部署环境

`initdb/*.sql` **不会**对已有 MySQL 数据目录重放。发 jar 之外必须手动执行一次：

```bash
docker exec -i quanta-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 ry-vue < cloudrun/quanta-mysql/initdb/11_patch_access_metric.sql
```
